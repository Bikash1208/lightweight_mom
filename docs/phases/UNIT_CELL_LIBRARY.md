# Production unit-cell library (Phase 7)

A rectangular-PEC-patch unit-cell library built from the **existing, unmodified** MoM solver
(Phases 1-6A), for a downstream holographic-metasurface geometry search. This file documents the
pipeline and the decisions behind it; the numbers themselves (phase coverage, resonance counts,
failed cells, ...) live in the generated `results/unit_cell_library/reports/LIBRARY_REPORT.md`,
which is regenerated by every build and is the authoritative record of what a given build actually
produced -- this file does not repeat them.

```
LibraryConfig (locked spec)  --> library_builder.py  --> Database (Phase 5, unmodified)
                                                                |
        +----------------------+----------------------+--------+-------+-----------------+
        |                      |                      |                |                 |
  phase_extraction.py   library_classifier.py   geometry_export.py  library_plots.py   library_validation.py
        |                      |                      |                |                 |
        +----------------------+----------------------+--------+-------+-----------------+
                                                                |
                                                    unit_cell_library.py (manifest, JSON/CSV,
                                                    LIBRARY_REPORT.md, query API)
```

## 1. Locked configuration and its authoritative source

Period 4.8 x 4.8 mm; substrate `Rogers RT/Duroid 5880` (`eps_r=2.2`, `tan_delta=0.0009`,
`thickness=1.575 mm`) -- these three substrate values are not invented for Phase 7: they are read
from, and checked against, this project's own root `config.yaml`
(`tests/test_library_schema.py::test_default_substrate_matches_project_authoritative_config_yaml`).
10-15 GHz, 25 MHz step, 201 points, design frequency 12.5 GHz (an exact grid point, index 100).
18x18 rectangular patches, L and W each 1.0-4.4 mm in 0.2 mm steps, 324 geometries
(`src/library_schema.py::LibraryConfig.default`).

## 2. Mesh and Floquet order: a measured decision, not a guess

The obvious mesh choice -- 24x24 cells (0.2 mm pitch, exactly the L/W sweep step, in principle
zero staircase error) -- was tried first and rejected for a concrete, reproducible reason: for
about 200 of the 324 geometries it misclassifies an entire extra mesh row/column due to
floating-point rounding in the unmodified mesh-boundary comparison (measured area errors up to
44%, `tests/test_library_builder.py::test_24x24_mesh_has_large_area_error_for_some_sweep_geometries`).
This is the same class of pitfall `src/validation_cases.py`'s module docstring documents for
Phase 6's case03, generalized: a feature edge that lands exactly on a mesh line is fragile to a
few ULP of rounding.

The library instead uses **32x32 cells, Floquet order 32** (`library_schema.DEFAULT_MESH`):
avoids that exact-coincidence pathology (dx = 0.15 mm shares no simple ratio with the 0.2 mm
step), satisfies the mesh rank rule with a large margin (`2*32+1=65 >= 32`), and was chosen after
directly timing the full 324-geometry grid at several mesh/Floquet combinations (24x24: fast but
pathological; 32x32: ~2.5 h for the full 324x201 build; 48x48, which does give exactly 0%
staircase error everywhere: ~19.6 h, measured directly and rejected as impractical). This mesh is
below this project's own "Floquet order 2-4x cells" practical accuracy guideline
(`MOM_FORMULATION.md`) purely for that build-time reason; every cell's a priori
`metal_area_error`/`area_ok` (`discretization.check_cell`, Phase 5, unmodified) is computed and
stored, not hidden -- see `LIBRARY_REPORT.md`'s "Limitations" section for the actual measured
distribution of a given build.

### 2A. Consequence of that mesh choice: many geometries are mesh-identical (Phase 12B)

The 32x32 mesh above was chosen to *avoid* the 24x24 pathology and stay well under the 48x48
build-time cost, but it does not exactly align every feature edge of the 18-value, 0.2 mm-step
L/W family (dx = 0.15 mm shares no simple ratio with 0.2 mm, by design, Sec. 2 above). A real,
measured consequence: **of the 324 (L, W) geometries in this library, only 169 discretize to a
distinct metal mask on this mesh; the other 155 fall into 105 duplicate groups** (two or more
geometries whose staircased pattern is bit-identical, hence bit-identical Z, V and S at every
frequency) -- `src/phase12b/duplicate_audit.py::phase7_library_duplicate_report`, cross-checked
against an independent count of distinct *solved* S11_xx values at 12.5 GHz in the delivered
lookup table (same 169/105 split). This does not change any solved value already in this
library -- it only means fewer than 324 of its rows carry independent information. See
`PHASE12B_MESH_PERIOD_STUDY.md` for the full duplicate-group listing and for what mesh would
avoid this (48x48 cells exactly aligns this family, matching Sec. 2's own already-measured "exactly
0% staircase error everywhere" finding for that mesh -- rejected there purely for build-time cost,
not because it doesn't work).

## 3. Reused, unmodified APIs

* `config.config_from_dict` (Phase 1) -- every per-cell `SimulationConfig`.
* `sweep.ParameterAxis`, `sweep.SweepDefinition`, `sweep.FrequencyGrid`, and `runner.run_sweep`
  (Phase 5) -- the actual solve, with its checkpointed/resumable, deterministic, `on_invalid`
  machinery reused exactly as the Phase 5 sweeps already were (`library_builder.py` only builds
  the axes/definition; it does not call the solver directly).
* `discretization.check_cell` / `is_specular_only` / `grating_onset_frequency` (Phase 4/5) --
  mesh-quality and grating-risk numbers, not re-derived.
* `cad_export.py` (Phase 6) -- STEP export, unchanged; `geometry_export.py` only adds deterministic
  filenames and an independent bounds re-check on top of it.
* `validation_export._db` / `_DB_FLOOR` (Phase 6) -- the one dB definition/floor used everywhere
  in this project, reused directly rather than reimplemented, per req. 23's "do not create a
  second incompatible S-parameter convention".
* `database.CONVENTIONS`, `phase.wrapped_difference_deg`, `phase.principal_phase_deg` (Phase 5) --
  the manifest's/library's `time_convention`/`polarization_convention` strings and every phase
  comparison.

## 4. Phase source: S11, with an honest caveat

`phase_extraction.resolve_phase_source()` returns `component="S11_xx"`,
`status="SPECIFICATION_MANDATED"` -- not `"PHYSICALLY_VALIDATED"`. The Phase 7 brief's own
lookup-table schema names S11 explicitly, so that choice is not guessed; but this project's
solver stack has **no ground plane** (README "Assumptions"), so unlike a typical grounded
reflectarray/holographic-antenna element, S21 here is *not* negligible (Phase 6's case01 measured
mostly-transmissive behaviour, not mostly-reflective). Whether the eventual holographic generator
actually needs S11 or S21 phase is an architecture decision (reflective vs. transmissive hologram,
and whether a ground plane will be added later) this project has not made and this module does
not invent. Both S11 and S21 (all four S-blocks) are stored in full regardless; only the
phase-vs-geometry table, coverage, collision and resonance analyses are pinned to S11.

## 5. Phase coverage: computed, not asserted

`phase_extraction.phase_coverage` sorts every successful cell's wrapped design-frequency phase
around the circle and reports the single largest empty arc (`largest_gap_deg`) and
`coverage_deg = 360 - largest_gap_deg`, alongside the plain (non-circular) min/max/span --
deliberately *not* a single "phase coverage = X%" number computed by counting occupied bins,
which could overstate coverage for a clustered set of points. See `plots/phase_coverage_map.png`
for the same information as a picture (the largest gap shaded on the unit circle) and
`tests/test_phase_extraction.py`'s synthetic-input tests (evenly spaced points, a single point,
a wrap-around case, a clustered case) for the arithmetic's correctness independent of any solver
output.

## 6. Classification: independent flags, documented thresholds

Every cell gets independent `geometry_status` (VALID/INVALID), `solver_status` (OK/FAILED),
`resonance` (RESONANT/NON_RESONANT/UNCLASSIFIED, from a documented local-maximum-prominence
criterion, `library_schema.RESONANCE_MIN_PROMINENCE`), `phase_status` (PHASE_USABLE/
PHASE_UNUSABLE/UNCLASSIFIED, from `library_schema.PHASE_USABLE_MIN_MAG_DB`) and `grating`
(GRATING_RISK/OK, from the existing `discretization.is_specular_only`) flags -- not one
mutually-exclusive label, since a cell can be RESONANT and PHASE_USABLE at once. Every threshold
is a named constant in `src/library_schema.py`, documented there with its rationale, and
exercised at its exact boundary in `tests/test_library_classifier.py`.

## 7. What this library does **not** do

* No EM formulation, Green's function, MoM matrix, basis functions or S-parameter code was
  touched to build it (Phases 1-6A are consumed exactly as they were).
* No HFSS comparison is performed or claimed. `library_validation.py` produces a deterministic
  *recommended* validation subset (`HFSS_VALIDATION_SUBSET.csv`) and says explicitly, in
  `LIBRARY_VALIDATION.md`, that no HFSS data has been imported.
* No geometry interpolation or extrapolation, anywhere, including in the query API
  (`UnitCellLibrary.get_cell`/`.response`/`.find_phase_candidates`/`.invert_phase`): every lookup
  is an exact match against a geometry/frequency actually simulated, or an explicit failure
  (`KeyError`, `ValueError`, or the literal string `"NO_VALID_CANDIDATE"`).
* No phase unwrapping anywhere in the stored/served data (`phase_series_deg`'s default,
  unmodified).
* No silent substitution for a failed cell; `runner.run_sweep`'s existing behaviour (an
  unexpected solve exception aborts the whole build rather than being caught and papered over) is
  relied on unchanged -- see `src/library_builder.py`'s module docstring.

## 8. Building and querying

```bash
.venv/bin/python examples/build_unit_cell_library.py            # results/unit_cell_library/ (resumable, hours)
.venv/bin/python examples/inspect_unit_cell_library.py           # query demo
```

Programmatically: `library_schema.LibraryConfig.default()`, `unit_cell_library.build_full_library`,
and `unit_cell_library.UnitCellLibrary.from_json(".../unit_cell_library.json")` for read-only
queries afterward (`get_cell`, `response`, `find_phase_candidates`, `invert_phase`).
